Tortoise and Hare: Floyd's Cycle Detection

Some number sequences march on forever. Others sneak into an infinite loop and just keep repeating. How do you tell the difference — without an infinite amount of memory to remember every number you've ever seen? The answer borrows its name straight from Aesop's fable.

No math background needed Two pointers Interactive
LEVEL 1

The mission: does this chain of numbers ever loop?

Imagine a rule that turns one number into the next: start with some number, apply the rule to get the next one, apply it again, and again, forever. This makes a chain: x₀ → x₁ → x₂ → x₃ → …

Two things can happen to a chain like this:

  • It keeps producing new numbers forever, never repeating (or it eventually lands on a number that stops the process, like reaching 1).
  • At some point, it reaches a number it has already seen before — and then it's doomed to repeat that same loop of numbers forever.

The question this page answers: given the rule and a starting number, how do you detect whether the chain loops — and even find exactly where the loop starts and how long it is — without storing every number you've ever visited?

Where does the name come from?

This algorithm is nicknamed the tortoise and hare algorithm, after Aesop's fable about the slow-but-steady tortoise and the fast-but-careless hare. It uses two "runners" moving through the same chain of numbers at different speeds — and, just like in the fable, the race has a surprising ending.

Why not just remember every number?

You could keep a list (or a set) of every number you've ever seen, and check each new number against it. That works! But it uses more and more memory the longer the chain gets — and in some real problems (imagine a chain with billions of steps, or one living inside a computer's memory where you can't just casually inspect everything), that's a serious cost. The tortoise and hare trick solves the same problem using only two variables, no matter how long the chain turns out to be.

Every single number eventually loops

Here's a nice fact: every starting number under this rule eventually enters a loop — either the tiny "loop" of just {1} (happy numbers), or that same 8-number unhappy loop {4, 16, 37, 58, 89, 145, 42, 20} that every unhappy number eventually falls into. There's no third option. So "is this number happy?" is really just "which loop does its chain eventually fall into?" — exactly the kind of question our algorithm is built to answer.

LEVEL 3

The obvious way: remember everything you've seen

The simplest approach: keep a set of every number visited so far. Before moving to the next number, check if it's already in the set. If it is, you've found a loop. If you ever reach 1, it's happy.

happy_naive.py
def next_number(x):
    return sum(int(d) ** 2 for d in str(x))

def is_happy_naive(x):
    seen = set()
    while x != 1 and x not in seen:
        seen.add(x)
        x = next_number(x)
    return x == 1

This works perfectly, and for a problem this small, it's genuinely a fine solution — the loop is short and the set never gets very big. But imagine a chain that runs for billions of steps before looping (this happens in other cycle-detection problems, like following pointers through a huge linked list). Storing billions of visited values would eat up all your memory. We need a way to detect the loop using only a small, fixed amount of extra space.

LEVEL 4

The clever idea: two racers, different speeds

Here's the trick. Put two "runners" on the same chain of numbers, both starting from the beginning:

  • The tortoise moves one step at a time: x → next(x).
  • The hare moves two steps at a time: x → next(next(x)).

If the chain runs forever without ever repeating, the hare just zooms off ahead of the tortoise and neither one ever needs to catch the other — nothing exciting happens (in our Happy Number example, this can't actually occur since every chain loops eventually, but it's the general shape of "no cycle found" in other settings, like a linked list ending in None).

But if the chain does loop — imagine the loop as an actual circular racetrack — then once both runners are on that circular track, the hare (moving twice as fast) is essentially lapping the tortoise. And on a circular track, a faster runner lapping a slower one always eventually catches up to the exact same spot. The tortoise and hare are guaranteed to land on the same number at the same time. That's your proof a loop exists!

Aesop's fable, but backwards

In the story, the hare loses the race by being careless. Here, the hare is doing exactly what it's supposed to — and its speed is precisely what guarantees it will eventually run right back into the tortoise, proving the racetrack loops. No carelessness required, just a factor-of-2 speed difference.

happy_floyd_detect.py
def next_number(x):
    return sum(int(d) ** 2 for d in str(x))

def is_happy_floyd(x):
    slow = next_number(x)
    fast = next_number(next_number(x))
    while slow != fast:
        slow = next_number(slow)
        fast = next_number(next_number(fast))
    return slow == 1

Only two variables, slow and fast — no matter how long the chain is before it loops. When they finally meet, check whether they met at 1 (happy) or somewhere else (unhappy, stuck in the 8-number loop).

LEVEL 5

Why does this actually work?

Here's the intuition, made precise. Suppose the chain has a "tail" of length μ (some numbers before the loop starts) followed by a loop of length λ (how many numbers are in the repeating part).

Once both the tortoise and the hare have entered the loop, think of their positions as points going around a circular track of λ spots. Every round, the tortoise advances 1 spot and the hare advances 2 spots — so the hare gains exactly 1 extra spot on the tortoise, every single round (measuring "how far ahead" the hare is, going around the loop).

Since the loop only has λ spots total, the gap between them (measured going around the loop) cycles through 0, 1, 2, …, λ−1, 0, 1, 2, … and back to 0 every λ rounds. A gap of 0 means they're standing on the exact same number. Since the gap increases by exactly 1 every round, it's guaranteed to hit 0 again within at most λ rounds after both runners are in the loop — it can't "jump over" 0, since it only ever changes by 1 at a time.

The takeaway

The meeting is not luck — it's guaranteed by simple arithmetic. And it happens quickly: within μ + λ rounds at the very most.

LEVEL 6

Going deeper: where does the loop start, and how long is it?

Knowing a loop exists is nice, but often you want more: exactly which number is the first one that gets revisited (this marks where the tail ends and the loop begins), and how many numbers are in the loop. Floyd's algorithm answers both, using two more short phases after the meeting point is found.

Phase 2: finding where the loop starts

Here's a small miracle: reset a new pointer, called finder, back to the very start of the chain. Leave the other pointer sitting right where the tortoise and hare met. Now move both of them one step at a time, together. The point where they meet this time is exactly the start of the loop.

Why does resetting to the start work?

It comes down to a bit of distance bookkeeping: by the time the tortoise and hare first met, the tortoise had traveled a distance that happens to be a multiple of the loop length λ, once you subtract off the tail length μ. That special relationship is exactly what makes walking from the very start, one step at a time, land on the loop's entrance at the same moment as walking one step at a time from the meeting point. It's a beautiful bit of arithmetic — you don't have to derive it yourself to trust it (though it's a fun proof to look up once you're comfortable with modular arithmetic).

Phase 3: measuring the loop's length

Once you know where the loop starts, measuring its length is easy: stay put at that number, and take single steps with another pointer, counting each step, until you land back on the same number. That count is λ.

floyd_full.py
def find_cycle(x0, next_fn):
    # Phase 1: detect that a cycle exists
    slow = next_fn(x0)
    fast = next_fn(next_fn(x0))
    while slow != fast:
        slow = next_fn(slow)
        fast = next_fn(next_fn(fast))

    # Phase 2: find where the cycle starts
    finder = x0
    while finder != slow:
        finder = next_fn(finder)
        slow = next_fn(slow)
    cycle_start = finder

    # Phase 3: measure the cycle's length
    length = 1
    p = next_fn(cycle_start)
    while p != cycle_start:
        p = next_fn(p)
        length += 1

    return cycle_start, length

LEVEL 9

Your turn: practice challenges

Work these out on paper first, then check yourself with the tool above.

Challenge 1: Trace the chain starting from 89 by hand. Is 89 happy? Where does it fall relative to the loop from Level 7?

89 → 8²+9²=145 → 42 → 20 → 4 → 16 → 37 → 58 → 89. It's unhappy, and since 89 itself is one of the 8 numbers in the loop, its tail length is μ=0 — it starts already inside the loop.

Challenge 2: If the tortoise and hare start at the very same number and that number is already inside a loop (tail length 0), will the very first comparison already show a match? Why or why not?

Not necessarily on the very first round — the tortoise has moved 1 step and the hare has moved 2 steps by the time of the first comparison, so unless the loop has length 1 (like the happy-number loop {1}, where every step stays at 1), they'll usually be at different points within the loop after round 1. They're still guaranteed to meet within λ rounds, per Level 5's argument — starting inside the loop just means μ=0, so the "at most μ+λ rounds" bound becomes "at most λ rounds."

Challenge 3: Why does the naive "remember everything in a set" approach from Level 3 use more and more memory as the chain gets longer, while the tortoise-and-hare approach doesn't?

The set-based approach stores every single number it has ever visited, so its memory usage grows in direct proportion to how many steps have happened — a chain with a million steps needs a set with up to a million entries. The tortoise-and-hare approach only ever keeps track of two current positions (slow and fast), no matter how long the chain turns out to be — it overwrites old positions instead of saving all of them, so its memory usage stays constant.

Challenge 4: This algorithm is famous for detecting cycles in linked lists (a chain of boxes, each pointing to the next one, where "next(x)" means "follow the pointer"). How would you adapt the Happy Number code from Level 4 to work on a linked list instead of numbers?

The shape of the algorithm barely changes — only what "one step" means. Instead of next_number(x) computing a digit-square-sum, you'd have slow = slow.next and (twice) fast = fast.next.next, moving along the list's pointers instead of applying a math formula. If the list has a cycle (some node's pointer loops back to an earlier node instead of ending at None), the fast pointer will eventually equal the slow pointer, exactly as before. If the list has no cycle, the fast pointer will simply reach the end (None) first, which tells you there's no cycle to find.

Challenge 5 (harder): Every unhappy number eventually falls into the exact same 8-number loop, {4, 16, 37, 58, 89, 145, 42, 20}. Using the naive set-based method from Level 3, roughly how would you go about proving this is the only unhappy loop that exists, for say all numbers from 1 up to 10,000?

Run the naive (or tortoise-and-hare) algorithm on every number from 1 to 10,000, and for each one that turns out unhappy, record the exact loop it eventually lands in (the set of numbers from where it starts repeating). Then compare all those recorded loops to each other. If every single one turns out to be the same 8-number set {4, 16, 37, 58, 89, 145, 42, 20}, that's strong empirical evidence (though not a mathematical proof for numbers beyond 10,000) that this is the only unhappy loop in that range. This is exactly the kind of experiment a programmer can run in a few seconds that would take forever by hand — and it's part of why this specific 8-number loop is so famous among Happy Number fans.

Floyd's Cycle Detection Algorithm (tortoise and hare) — a classic technique for detecting loops using only constant extra memory. It shows up everywhere from linked-list problems to number-theory puzzles like Happy Numbers, and even in cryptographic factoring algorithms like Pollard's rho.
