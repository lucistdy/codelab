Codeforces 711E · 题目精讲

生日悖论：驯服一个带 1018 的分数

在一个有 2n 天的一年里，ZS 采访了 k 个人。至少有两人生日相同的概率是多少？麻烦在于：n 和 k 都可以大到 1018——大到没法用直接的办法算出任何东西。

不需要数学基础 概率 & 数论 可以互动
第一关

任务目标，原样来自题目

乌代兰一年有 2n 天。ZS 采访了 k 个人，每个人的生日都从这 2n 天里均匀随机地选一天。他想知道至少有两人生日相同的概率，写成最简分数 A/B（A 和 B 没有公因数），然后对 106+3 取模输出。

题目原样给出的例子

n=3, k=2 → A=1, B=8  （8 天，2 个人，概率 1/8）
n=1, k=3 → A=1, B=1  （只有 2 天却有 3 个人——必然撞上！）
n=4, k=3 → A=23, B=128

这题为什么难？

n 和 k 各自最大可以到 1018。这意味着 2n 可能是一个位数多达几十亿亿的数字——根本存不下，更别说直接拿它算概率了。可题目还想要一个精确的、已经完全约分好的分数。这一页要讲的，就是让这件事变得可能的几个巧妙捷径。

第二关

等等，什么是生日悖论？

这是一个经典的派对小把戏：随便找 23 个人凑在一起，其中有两人生日相同的概率就已经接近 50% 了——尽管一年有 365 天，而只有 23 个人！大多数人第一次听到都会很震惊，因为 23 相比 365 实在显得太小了。

理解这件事的关键在于：你不是在检查有没有人跟你自己生日相同（那确实需要远不止 23 个人）。你是在检查这 23 个人里任意两个人之间有没有撞上——而 23 个人之间一共能组成 23×22/2 = 253 对不同的人，每一对都有可能撞上生日。253 次撞上的机会，累积起来速度非常快！

用大白话讲这道题

乌代兰的版本只是把"365 天"换成了"2n 天"，把"23 个人"换成了"k 个人"——而且它要的不是一个近似的百分比，而是精确的分数概率。

第三关

公式：把问题反过来问

"至少两人生日相同"直接计算起来很别扭——能发生这件事的方式太多了。反过来算简单得多：先算所有人生日都不相同的概率，再用 1 减去它。

想象一个一个采访过去，一共有 m = 2n 种可能的日子。第 1 个人生日随便什么都行（"暂时没撞上"的概率是 1）。第 2 个人必须避开第 1 个人占用的那天：概率 (m−1)/m。第 3 个人必须避开已经用掉的 2 天：概率 (m−2)/m。以此类推，一直到全部 k 个人：

P(不撞) = m⁄m × (m−1)⁄m × (m−2)⁄m × … × (m−k+1)⁄m

P(至少撞一次) = 1 − P(不撞)

对照样例一验证一下

对 n=3, k=2 来说：m=8。P(不撞) = 8/8 × 7/8 = 7/8。所以 P(撞) = 1 − 7/8 = 1/8。正好对上 A=1, B=8！

第四关

什么时候"撞生日"是 100% 确定的？

如果你想采访的人数比一年的天数还多，撞生日就不只是"很可能"了——而是板上钉钉。这就是经典的鸽笼原理：如果鸽子比鸽笼多，那至少有一个笼子里得塞两只鸽子。

这里，"鸽子"就是人，"鸽笼"就是天数。如果 k > 2n，答案立刻就是 P = 1，也就是 A=1, B=1——完全不需要计算！

对照样例二验证一下

对 n=1, k=3 来说：只有 21=2 天，却有 3 个人。因为 3 > 2，撞生日是必然的。输出：1 1。正好是题目给出的答案。

当 n 很大时的一个好用捷径

因为 k ≤ 1018，一旦 n ≥ 60，2n 就已经比 260 ≈ 1.15 × 1018 还大，而这已经比任何可能的 k 都大了。所以"必然撞上"这种情况只可能发生在 n 比较小（小于 60）的时候——这时 2n 小到完全可以直接算出来跟 k 比较，根本不会遇到大数字的麻烦。

第五关

真正的麻烦：大到写不下的数字

一旦确定撞生日不是必然的（也就是 k ≤ 2n），我们还是得算出第三关的那个公式——而这正是可怕的地方。n 最大到 1018 时，2n 会是一个大到地球上所有存储空间都写不下的数字。而 k 本身也可能让这个乘积有多达 1018 项——多到不可能一项一项去乘。

1018
最坏情况下乘积里的项数——不可能一个一个循环乘过去
≥ 1017 位
n 很大时，2n 写出来大概需要的位数——连存都存不下

所以我们需要找到一些捷径，能让我们直接算出最终答案，而完全不用在中间步骤里真正算出那些天文数字。接下来几关会一步一步搭建出正是这样的捷径。

第六关

关键洞察：答案的分母永远是 2 的幂

再看一眼第三关 P(不撞) 的公式：它的分母是 mk = (2n)k = 2n×k。就这样——一个纯粹的 2 的幂，里面不含任何别的质因子！

把一个分数约分到最简形式时，能约掉的只能是分子和分母共有的因子。既然这里的分母百分之百由 2 组成，那唯一可能被约掉的东西就只能是 2。这意味着：不管分子长得多复杂，约到最简之后的分母永远会是某个 2 的幂。

为什么这一点会改变一切

这把问题变成了一个窄得多的问题：分子里到底藏着多少个因子 2？只要能数清楚这一个数字，我们就立刻知道该约掉多少——而完全不用理会任何其他质因子。

第七关

数清楚这些 2：勒让德公式

P(不撞) 的分子是 2n × (2n−1) × (2n−2) × … × (2n−k+1)。第一项 2n 恰好贡献了 n 个因子 2，因为它本身就是纯粹的 2 的幂。剩下那些呢？

这里有个巧妙的事实：由于本题里 i 总是远小于 2n，对于每一个从 1 到 k−1 的 i，(2n − i) 里因子 2 的个数，其实正好等于 i 本身里因子 2 的个数。所以这些项加起来一共藏着的 2 的个数，就等于 1 × 2 × 3 × … × (k−1)，也就是 (k−1)! 里藏着的 2 的个数。

数清楚一个阶乘里有多少个因子 2，有个经典的捷径叫勒让德公式：不断除以越来越大的 2 的幂，再把商的整数部分加起来。

v2(m!) = ⌊m/2⌋ + ⌊m/4⌋ + ⌊m/8⌋ + …

举例算一遍：v2(10!)

⌊10/2⌋ + ⌊10/4⌋ + ⌊10/8⌋ + ⌊10/16⌋ = 5 + 2 + 1 + 0 = 8。所以 10! 能被 28 = 256 整除，但不能被 29 整除。（不放心的话可以再验证一遍：2、4、6、8、10 每个都至少贡献一个因子 2——一共 5 个。然后 4 和 8 各自还能多贡献一个——再加 2 个。然后 8 还能再多贡献一个——再加 1 个。总共 5+2+1=8。）

所以第三关分子里因子 2 的总数是：

V = n + v2((k−1)!)

第八关

第二个鸽笼技巧：提前停止相乘

我们还需要分子的奇数部分（把所有 2 都拿掉之后剩下的部分），并且要对质数 p = 1,000,003 取模。最朴素的做法——把全部 k 项一个一个乘起来再取模——如果 k 能到 1018，问题又回来了。

这里的救星是：p 本身"只不过"一百万左右。分子里的这些项，是 k 个连续递减的整数。只要连续排出 p 个或更多这样的整数，根据鸽笼原理，它们除以 p 的余数就必然会把从 0 到 p−1 的每一个余数都覆盖至少一次——包括余数 0！这就意味着其中必然有一项正好是 p 的整数倍。

这个捷径

所以：如果 k ≥ p，我们不用检查任何一项，就能确定这个乘积对 p 取模一定是 0。我们只有在 k < p 的时候才真的需要跑这个乘法循环，也就是说最多只需要大约一百万次迭代——不管题目允许的 k 有多么天文数字般巨大。

1018
题目允许的 k 的最坏情况
< 1,000,003
我们实际会执行的最多乘法步数
第九关

用模逆元把那些 2 除掉

现在我们有了两个对 p 取模后的原料：NumMod（用第八关的快捷方法算出的、分子完整取模后的值）和 V（第七关算出的、需要去掉的 2 的确切个数）。要在模运算的世界里"除掉" 2V，我们要改成乘以它的模逆元——这正是这个系列里反复出现的费马小定理技巧：

(2V)−1 mod p = (2V)p−2 mod p

把 NumMod 乘上这个逆元，就得到 OddMod——分子"除掉所有 2 之后剩下的部分"，取模后的值。接下来：

B = 2E， 其中 E = n×k − V  （约分之后分母里剩下的 2 的幂次）
A = B − OddMod  （因为 P(撞) = 1 − OddMod/B = (B−OddMod)/B）

为什么 A 和 B 自动就是互质的

因为 OddMod 来自一个已经把所有 2 都剥掉的数，所以它是奇数。用一个奇数去减一个 2 的偶数次幂（只要 E ≥ 1），结果永远是奇数。所以 A 是奇数，B 是纯粹的 2 的幂——它们之间没有大于 1 的公因数，正好满足题目"取模之前必须已经约分"的要求。

第十关

用 Python 把它写出来

是时候把第四到第九关的所有想法拼到一起写成代码了。Python 天生支持任意大小的整数，加上三参数的 pow(base, exp, mod)（能高效处理再大的指数），让这段代码短得惊人。

birthday_paradox.py
MOD = 1_000_003

def v2_factorial(m):
    total = 0
    p = 2
    while p <= m:
        total += m // p
        p *= 2
    return total

n, k = map(int, input().split())

# 第四关：撞生日是不是必然的？
if n < 63 and k > (1 << n):
    print(1, 1)
else:
    # 第七关：分子里因子 2 的总数
    V = n + v2_factorial(k - 1)

    # 第八关：分子取模，超过一百万项就直接短路
    n_mod = pow(2, n, MOD)
    if k >= MOD:
        num_mod = 0
    else:
        num_mod = 1
        for i in range(k):
            num_mod = num_mod * ((n_mod - i) % MOD) % MOD

    # 第九关：用模逆元把 2 都剥掉
    inv_2V = pow(pow(2, V, MOD), MOD - 2, MOD)
    odd_mod = num_mod * inv_2V % MOD

    E = n * k - V
    B = pow(2, E, MOD)
    A = (B - odd_mod) % MOD

    print(A, B)
if n < 63 and k > (1 << n): print(1, 1)
第四关的鸽笼捷径。先检查 n < 63 能避免在 n 天文数字般巨大时去真的计算 1 << n（反正在那种情况下也用不上，因为 k 永远不可能超过它）。
V = n + v2_factorial(k - 1)
第七关数因子 2 的方法，用勒让德公式——哪怕 k 是 1018，也只需要大约 60 次循环。
if k >= MOD: num_mod = 0 else: ... 循环 ...
第八关的第二个鸽笼捷径——只有在保证循环很短的时候才会真的去跑它。
E = n * k - V B = pow(2, E, MOD)
哪怕 n * k 大到 1036 左右，Python 也能精确算出来；pow(2, E, MOD) 内部用快速幂高效处理这个巨大的指数。
第十一关

一起手把手推演一遍：n=4, k=3

数字小到可以完全手算——而且应该正好对上题目的样例答案 23 128。

第十三关

该你练习了

先自己在纸上算出来，再用上面的工具验证。

挑战一：用勒让德公式算出 v2(6!)，再直接列出 1,2,3,4,5,6 里的因子 2 来交叉验证。

勒让德公式：⌊6/2⌋ + ⌊6/4⌋ + ⌊6/8⌋ = 3 + 1 + 0 = 4。直接验证：2 贡献一个 2，4 贡献两个 2（2×2），6 贡献一个 2——总共 1+2+1 = 4。两边一致：6! = 720 = 24 × 45。

挑战二：对 n=2, k=5 来说，撞生日是不是必然的？输出应该是什么？

22 = 4 天，却有 5 个人——因为 5 > 4，根据鸽笼原理，撞生日是必然的。输出：1 1，不需要再进一步计算。

挑战三：为什么代码要先专门检查 "n < 63" 再去算 1 << n，而不是每次都直接算出 2n 再比较？

因为 n 最大可以到 1018，这样的 n 对应的 2n 会是一个大得难以想象的数字——大到不可能在合理的时间或内存里把它算出来、存起来，或者拿去跟别的东西比较。但因为 k ≤ 1018 < 260，只要 n 达到 60 左右，我们不用真的算出 2n 的具体值，就已经能确定 2n > k——所以直接跳过"必然撞上"这个分支，转而用取模运算的方法继续算，这个方法处理超大的 n 完全没问题。

挑战四：用你自己的话解释一下，为什么一旦 k ≥ 1,000,003，分子对 p 取模的结果必然是 0——而且不需要做任何乘法。

分子是 k 个连续递减整数的乘积：2n, 2n−1, 2n−2, …。任意 p 个连续的整数，看它们除以 p 的余数，必然会把从 0 到 p−1 的每一个可能余数都恰好覆盖一次（因为它们是连续的，一共正好 p 个，不可能跳过任何一个余数）。既然 0 也是可能的余数之一，那这些项里就必然有一项恰好是 p 的整数倍——而任何数乘上 p 的倍数，结果对 p 取模也是 0。只要 k 至少是 p，乘积里就必然包含至少 p 个连续的项，所以这个结论永远成立。

挑战五（较难）：修改第十关的代码，让它在 n=0（也就是一年只有 1 天）时也能正确运行。这种情况应该发生什么，现有代码是不是已经能正确处理了？

当 n=0 时，一年只有 20=1 天，而题目本身的约束保证了 k ≥ 2，所以一定有 k ≥ 2 > 1 = 2n——也就是说鸽笼检查 n < 63 and k > (1 << n) 会立刻捕获这种情况，直接打印 1 1，正确反映了"只有一天可选，任何 2 个或更多人都必然撞上"这件事。完全不需要额外改代码——第一步检查就已经处理好了。
