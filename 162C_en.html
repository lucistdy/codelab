Prime Factorization: Every Number's Secret Recipe

Every whole number bigger than 1 is secretly built out of prime numbers multiplied together — and there's only ever one correct recipe. Your job: given a number n, print out its exact recipe, smallest prime first.

LEVEL 1

The mission, straight from the judge

You're given a whole number n (somewhere between 2 and 10,000). Every such number can be written as a product of prime numbers — its prime factorization. Your job is to print that product out, factors listed from smallest to largest, separated by *, with repeated primes printed multiple times.

Straight from the judge

n = 245 → 5*7*7  (because 245 = 5 × 7 × 7)
n = 19 → 19  (19 is already prime, so it's its own one-ingredient recipe)

A fact worth knowing: the Fundamental Theorem of Arithmetic

Here's something remarkable: for any whole number bigger than 1, there is exactly one way to write it as a product of primes (ignoring the order you multiply them in). Not two ways, not zero — exactly one. Mathematicians call this the Fundamental Theorem of Arithmetic, and it's the whole reason "the prime factorization of n" is a well-defined thing to ask for in the first place.

LEVEL 2

What's a prime, again?

A prime number is a whole number greater than 1 whose only divisors are 1 and itself — it can't be split into two smaller whole-number factors. 2, 3, 5, 7, 11, 13, 17, 19… are all primes. A number that can be split, like 12 = 3 × 4, is called composite.

Think of primes as the periodic table of numbers — the "atoms" that everything else is built from by multiplying. 12 = 2 × 2 × 3, 100 = 2 × 2 × 5 × 5, 245 = 5 × 7 × 7. No matter how you slice it, breaking a number down far enough always bottoms out at the same set of prime "atoms."

LEVEL 3

The simple method: keep dividing by the smallest thing that works

Here's an approach that's almost embarrassingly simple, and it works perfectly: start testing divisors from 2 upward. Whenever the current divisor d evenly divides what's left of n, record d as a factor and divide it out — and keep dividing by that same d as many times as it keeps working, before moving on to the next candidate.

Let's hand-trace n = 245:

  • Try d=2: 245 is odd, doesn't divide. Move on.
  • Try d=3: 245 ÷ 3 isn't whole. Move on.
  • Try d=4: nope. Move on.
  • Try d=5: 245 ÷ 5 = 49 exactly! Record a 5, and now we're factoring 49 instead.
  • Try d=5 again on 49: 49 ÷ 5 isn't whole. Move to the next divisor.
  • Try d=6: nope. Try d=7: 49 ÷ 7 = 7 exactly! Record a 7, now factoring 7.
  • Try d=7 again on 7: 7 ÷ 7 = 1 exactly! Record another 7. Nothing left to factor.

Recorded factors, in the order we found them: 5, 7, 7 — already smallest-to-largest, exactly matching the judge's expected output 5*7*7.

Why this never records a non-prime divisor by accident

Notice we always try the smallest untested divisor first, and we fully divide it out before moving on. That guarantees every number we ever record is prime: if some composite number like 4 or 6 could still divide what's left, then a smaller prime factor of that composite (like 2 or 3) would have already divided it out earlier, since we never skip ahead.

LEVEL 4

The smart shortcut: stop checking at √n

The plain version of this method checks divisors d = 2, 3, 4, … all the way up to n itself. But here's a shortcut: once d × d is bigger than what's currently left of n, you can stop — whatever's left over (if anything bigger than 1) must itself be one single leftover prime factor.

Why? If the remaining number n had two factors both bigger than √n, their product would already be bigger than n — impossible. So at most one factor of n can be bigger than √n, and if such a factor exists, it has to be n itself (already fully reduced, with no smaller prime factors left to find).

LEVEL 5

Writing it in Python

Here's the whole algorithm from Levels 3 and 4, written out. Read the code on the left, then the plain-English note on the right.

prime_factorization.py
n = int(input())

factors = []
d = 2
while d * d <= n:
    while n % d == 0:
        factors.append(d)
        n //= d
    d += 1

if n > 1:
    factors.append(n)

print("*".join(map(str, factors)))

LEVEL 8

Your turn: practice challenges

Work these out on paper first, then check yourself with the tool above.

Challenge 1: Find the prime factorization of n=360 by hand.

360 ÷ 2 = 180, 180 ÷ 2 = 90, 90 ÷ 2 = 45 (45 is odd, done with 2's — that's three 2's). 45 ÷ 3 = 15, 15 ÷ 3 = 5 (5 isn't divisible by 3 — that's two 3's). d=4 doesn't divide 5, and d=5: 5×5=25 > 5, so the loop stops with n=5 left over. Final answer: 2*2*2*3*3*5. Check: 8 × 9 × 5 = 360. ✓

Challenge 2: What does the output look like for n=2, the smallest possible input?

The loop condition is d*d ≤ n, i.e. 4 ≤ 2, which is false right away — the loop body never runs. Since n=2 > 1 at the end, we append it directly. Output: just 2.

Challenge 3: Why does the inner loop (while n % d == 0) need to exist at all — why not just check each d once and move on?

Because primes can appear more than once in a factorization — like the two 7's in 245 = 5 × 7 × 7, or the four 2's in 16 = 2×2×2×2. If we only checked each d once and immediately moved to d+1, we'd only ever record each prime a single time, and the output would be missing repeats. The inner loop keeps dividing out the same d for as long as it keeps working, which is exactly how repeated prime factors get counted correctly.

Challenge 4: Modify the code so that instead of printing repeated factors like 2*2*2*5*5*5*5, it prints each prime with an exponent, like 2^3 * 5^4.
prime_factorization_exponents.py
n = int(input())

parts = []
d = 2
while d * d <= n:
    if n % d == 0:
        count = 0
        while n % d == 0:
            count += 1
            n //= d
        parts.append(f"{d}^{count}")
    d += 1

if n > 1:
    parts.append(f"{n}^1")

print(" * ".join(parts))

Same core loop as before, except now we count how many times each d divides before moving on, instead of appending it once per division.

Challenge 5 (harder): For n = 9409 = 97 × 97, explain why the loop still finds both 97's even though d only ever reaches 97, which is exactly √9409.

The loop condition is d*d ≤ n. When d=97, we have 97 × 97 = 9409 ≤ 9409 — true, so the loop body still runs one more time. Inside, 9409 % 97 == 0, so 97 gets recorded and n becomes 9409 // 97 = 97. The inner loop checks again: 97 % 97 == 0, so a second 97 gets recorded, and n becomes 1. Only then does the outer loop stop (since n is now 1, and d*d would exceed it). Both copies of 97 get found correctly, right at the boundary of the √n shortcut.
