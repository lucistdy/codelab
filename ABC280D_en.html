Factorial and Multiple: Working Legendre's Formula Backwards

You already know how to check whether N! is divisible by some number K. This problem flips the question around: given K, find the smallest N for which that's true. It sounds like it needs a giant search — but the exact same tool that counts trailing zeros of a factorial, run backwards with a bit of binary search, cracks it in a heartbeat.

LEVEL 1

The mission, straight from the judge

You're given an integer K (2 ≤ K ≤ 1012). Find the smallest positive integer N such that N! (the factorial of N, meaning 1 × 2 × 3 × \cdots × N) is a multiple of K.

Straight from the judge

K = 30 → N = 5  (because 5! = 120 = 30 × 4, and no smaller factorial works: 1!, 2!, 3!, 4! are 1, 2, 6, 24, none divisible by 30)
K = 280 → N = 7  (7! = 5040 = 280 × 18)
K = 123456789011 → N = 123456789011  (the answer equals K itself!)

Why you can't just try N = 1, 2, 3, … one at a time

Look at that third sample: the answer can be as large as K itself, up to 1012. Actually computing N! for N that big — or even just multiplying up to it step by step — is completely hopeless. A trillion multiplications, each on a number with hundreds of digits, would never finish in time. We need a way to jump straight to the answer.

LEVEL 2

Turning "divisible by K" into a question about primes

Here's the idea that unlocks everything. Any number K breaks down uniquely into primes: K = p₁e₁ × p₂e₂ × \cdots × pₖeₖ. And N! is a multiple of K exactly when N! contains at least eⁱ copies of every one of those primes pⁱ.

So the problem splits into two much smaller problems:

  • Factor K into its prime powers.
  • For each prime power pe in that factorization, work out the smallest N whose factorial contains at least e copies of p.
Why we then take the maximum, not the sum

Once we know the smallest N needed to satisfy each individual prime in K's recipe, the smallest N that satisfies all of them at once is simply the largest of those individual answers. That's because N!'s supply of every prime only ever grows as N grows — so once N is big enough for the "neediest" prime, every other prime's requirement is automatically already satisfied too.

Check it against sample 1: K = 30 = 2 × 3 × 5. The smallest N whose factorial contains a 2 is N=2. For a 3, it's N=3. For a 5, it's N=5. The answer is max(2, 3, 5) = 5 — matching the judge exactly.

LEVEL 3

Counting copies of a prime inside N! — Legendre's formula

We need a fast way to answer: "how many times does prime p divide into N!?" You can't just count multiples of p up to N — a number like p² contributes two copies of p, not one. The clean way to count all of them, counting every extra copy correctly, is Legendre's formula:

⌊N/p⌋
+
⌊N/p²⌋
+
⌊N/p³⌋
+ …
exponent_in_factorial.py
def exponent_in_factorial(n, p):
    total = 0
    power = p
    while power <= n:
        total += n // power
        power *= p
    return total
Seen this formula before?

This is exactly the tool built (and explained in full) on the Trailing Loves page, where it's used to count trailing zeros of N! in any base. There, you're given N and asked how many times a prime divides its factorial. Here, we're about to use the same function, but ask a very different question of it.

LEVEL 4

Running the formula backwards with binary search

Legendre's formula answers "given N, how many copies of p?" We need the opposite: "given that we need at least e copies of p, what's the smallest N?" Here's the key fact that makes this easy: as N grows, the count from Legendre's formula never decreases. Bigger factorials only ever pick up more copies of p, never fewer.

Whenever a quantity only ever increases (or stays the same) as you move a candidate value up, binary search becomes the perfect tool for finding the exact crossover point — the smallest N where the count first reaches the target e. Instead of checking N = 1, 2, 3, \ldots one at a time, binary search finds it in only about log₂(N) guesses.

Where do we even start searching?

We need an upper bound we're sure is big enough. Here's a simple one: Legendre's formula's very first term alone, ⌊N/p⌋, already reaches e once N = p × e (since ⌊(p×e)/p⌋ = e exactly). So N = p × e is guaranteed to be large enough to search up to — we never need to guess higher than that.

min_n_for_prime_power.py
def min_n_for_prime_power(p, e):
    lo, hi = 1, p * e  # floor((p*e)/p) = e already, so hi is always large enough
    while lo < hi:
        mid = (lo + hi) // 2
        if exponent_in_factorial(mid, p) >= e:
            hi = mid
        else:
            lo = mid + 1
    return lo
LEVEL 5

Factoring K fast enough

The last ingredient: breaking K into its prime powers in the first place. Since K ≤ 1012, the same √K trial-division shortcut from the Prime Factorization page does the job — test candidate divisors up to √K (about a million, since √(1012) = 106), dividing each one out fully before moving on.

factorize.py
def factorize(k):
    factors = {}
    d = 2
    while d * d <= k:
        while k % d == 0:
            factors[d] = factors.get(d, 0) + 1
            k //= d
        d += 1
    if k > 1:
        factors[k] = factors.get(k, 0) + 1
    return factors

Why sample 2's answer equals K itself

123456789011 happens to be a prime number — so its own factorization is just itself, to the power 1. The smallest N whose factorial contains even one copy of that giant prime is N equal to the prime itself (nothing smaller than a prime p is ever divisible by p, so p can't show up in any factorial before N reaches p). This is exactly why the answer can be as large as K — and exactly why brute-force computing factorials was never going to work.

The complete program:

abc280d.py
def factorize(k):
    factors = {}
    d = 2
    while d * d <= k:
        while k % d == 0:
            factors[d] = factors.get(d, 0) + 1
            k //= d
        d += 1
    if k > 1:
        factors[k] = factors.get(k, 0) + 1
    return factors

def exponent_in_factorial(n, p):
    total = 0
    power = p
    while power <= n:
        total += n // power
        power *= p
    return total

def min_n_for_prime_power(p, e):
    lo, hi = 1, p * e
    while lo < hi:
        mid = (lo + hi) // 2
        if exponent_in_factorial(mid, p) >= e:
            hi = mid
        else:
            lo = mid + 1
    return lo

def solve(k):
    factors = factorize(k)
    return max(
        min_n_for_prime_power(p, e)
        for p, e in factors.items()
    )

k = int(input())
print(solve(k))

Challenge 1: Find the smallest N such that N! is a multiple of K = 100 by hand.

100 = 2² × 5². Smallest N with two copies of 2: N=4 gives ⌊4/2⌋+⌊4/4⌋=3, already enough (N=3 gives only 1, so N=4 is needed... let's check N=4 vs smaller: actually we need ≥2 copies of 2, and N=4 gives 3 copies, N=3 gives 1 copy — so smallest is N=4). Smallest N with two copies of 5: need ⌊N/5⌋+⌊N/25⌋ ≥ 2, which first happens at N=10 (⌊10/5⌋=2). Answer: max(4, 10) = 10. Check: 10! = 3628800 = 100 × 36288. ✓

Challenge 2: Why does the smallest N for a prime power p² sometimes need N to be much bigger than 2p?

Because after the first multiple of p (contributing one copy), the next copy doesn't necessarily come from the very next multiple of p — it comes from the second multiple of p, which is 2p. So two copies of p typically need N to reach 2p, not just a little past p. For larger exponents, this "spread out" effect compounds, which is exactly why Legendre's formula (summing over all powers of p) is needed instead of simple guesswork.

Challenge 3: Why is it safe for the binary search to use hi = p × e as a starting upper bound, no matter how large e is?

Legendre's formula's very first term alone is ⌊N/p⌋, and every other term only adds more. When N = p × e, that first term equals exactly e (since p × e divides evenly by p). So the total count at N = p × e is automatically at least e, regardless of how big e gets — guaranteeing the true answer is never bigger than this starting upper bound.

Challenge 4 (harder): If K is a perfect square of a prime, like K = p², is the answer always exactly 2p?

Not necessarily — it depends on p. For small p, extra copies of p can appear "for free" before N reaches 2p. Take p=2: for K=4=2², we need ≥2 copies of 2 in N!. At N=4, Legendre gives ⌊4/2⌋+⌊4/4⌋=2+1=3 — already satisfied, and even N=3 (⌊3/2⌋=1) isn't enough, so the true minimal N is 4, which does equal 2p here. But try p=2, e=3 (K=8): N=4 gives 3 copies exactly (as computed above), and that's already the minimal N — smaller than 2×p×(e/2) type guesses might suggest. The exact answer always requires running Legendre's formula (or the binary search); there's no universal shortcut formula that skips it, which is exactly why Level 4's binary search approach is the reliable way to go.

Challenge 5: Modify the Python code so that instead of just returning the final answer, it also prints, for each prime factor of K, the minimal N that prime alone would require — useful for seeing which prime is the bottleneck.

def solve_debug(k):
    factors = factorize(k)
    best = 0
    for p, e in factors.items():
        n = min_n_for_prime_power(p, e)
        print(f"prime {p}^{e} needs N >= {n}")
        if n > best:
            best = n
    return best
