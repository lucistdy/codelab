Scary Primes: The Numbers That Survive Getting Chopped From the Front

Take a prime number. Chop off its leftmost digit. Is what's left still prime? Chop again. Still prime? Keep going until only one digit remains. A prime that survives this entire ordeal — and never once shows a digit 0 — earns the title "scary prime." Your job: count how many of them exist up to some number N, and answer up to 100,000 such questions without breaking a sweat.

No math background needed Sieve of Eratosthenes & Precomputation Interactive
LEVEL 1

The mission, straight from the judge

You'll be asked up to T = 100,000 questions, each one just a single number N (1 ≤ N < 1,000,000). For each one, answer: how many scary primes are there that are less than or equal to N?

A number is a scary prime if all of the following are true:

  • It's prime.
  • None of its digits is 0.
  • If you delete its leftmost digit, what remains is also a scary prime — and you can keep deleting the new leftmost digit, over and over, all the way down to a single leftover digit, and every single stage along the way stays prime.
Straight from the judge

Input: 3 (three questions), then 2, 3, 4 — one per line.
Output: 1, 2, 2.
Why? Up to 2, the only scary prime is 2 itself — that's 1. Up to 3, we also get 3 — that's 2. Nothing new shows up between 3 and 4 (4 isn't even prime), so it's still 2.

A bigger example to really see it in action

The seven-digit number 4632647 is scary. Watch what survives as we chop from the left, one digit at a time: 4632647 → 632647 → 32647 → 2647 → 647 → 47 → 7. Every single one of those seven numbers is prime, and not one of the seven original digits is a 0. That's what it takes to earn the "scary" badge.

Why does chopping ever stop working?

Try it with a random prime, like 29: chop the 2 off the front, and you're left with 9 — which isn't prime (9 = 3 × 3). So 29 fails immediately and is not scary, even though 29 itself is a perfectly good prime. Most primes fail this test almost right away — scary primes are rare, and that's exactly what makes counting them an interesting puzzle.

LEVEL 2

Refresher: primes and the Sieve of Eratosthenes

A prime is a whole number greater than 1 whose only divisors are 1 and itself. To find every prime up to some limit fast, we use the Sieve of Eratosthenes: start by assuming every number is prime, then for each prime you find, cross out every multiple of it (2 crosses out 4, 6, 8, …; 3 crosses out 6, 9, 12, …; and so on). Whatever survives every crossing-out is prime.

sieve.py
LIMIT = 1_000_000
is_composite = bytearray(LIMIT + 1)
is_composite[0] = is_composite[1] = 1

for i in range(2, int(LIMIT**0.5) + 1):
    if not is_composite[i]:
        for j in range(i * i, LIMIT + 1, i):
            is_composite[j] = 1
Already met the sieve before?

If you've read the Prime Number Detective Agency case file, this will look familiar — it's the exact same sieve. Here, though, finding primes is only step one. The real puzzle is what happens next.

LEVEL 3

Why checking one number at a time is way too slow

The obvious plan: for every query N, loop through all numbers from 2 to N, and for each one, check "is it prime, digit-free of zero, and does chopping its front digit repeatedly always stay prime?" That's a perfectly correct plan — and a disastrously slow one.

The fix, in one sentence

Do all the hard thinking once, before any questions arrive — figure out, for every number up to 999,999, whether it's scary, then build a running tally so any question can be answered instantly by looking up one number in an array.

LEVEL 4

The key trick: build up small answers first

Here's the insight that makes this whole problem click. To know if a number n is scary, we need to know if the number left over after chopping its front digit — call it its suffix — is also scary. But that suffix is always smaller than n (it has fewer digits, or at worst the same value if n is a single digit). That means: if we process every number in increasing order, from 2 up to 999,999, the answer for the suffix will already be sitting there waiting for us by the time we need it.

4632647
→ suffix
632647
← already decided!

This is the same "solve the small pieces first, reuse them for the big piece" idea behind dynamic programming everywhere — you may have seen it for computing Fibonacci numbers or counting paths. Here, the "small piece" of a number is just its own suffix, which we happen to visit earlier simply by counting upward.

What exactly is "the suffix"?

If n has k digits, its suffix (after removing the leftmost digit) is just n % 10k-1 — the remainder when you divide by the right power of 10. For 4632647 (7 digits), the suffix is 4632647 % 1000000 = 632647. Keep taking remainders with smaller and smaller powers of ten (% 100000, % 10000, …, % 10) and you walk through every stage of the chopping, from "just the front digit removed" all the way down to "just the last digit remains."

LEVEL 5

The one trap: arithmetic doesn't know about leading zeros

Here's a subtlety that catches almost everyone the first time. Suppose a number contains a 0 somewhere in the middle, like 907. If we chop off its front digit using 907 % 100, we get 7 — not "07". Arithmetic silently swallows leading zeros. But 907 is supposed to be disqualified for containing a 0 digit at all — and if we only checked "is the remainder prime," we'd never notice, because 7 genuinely is prime!

The fix: check for zero digits separately, up front

Before doing any chopping logic at all, look at every digit of the number directly (as a string, or by repeatedly checking n % 10) and reject it immediately if a 0 shows up anywhere. Only numbers that pass this check even get considered for the chopping test.

A fun mathematical fact

Numbers like this — primes that stay prime as you chop digits off the front, one at a time — are called left-truncatable primes in mathematics. It turns out there are only 4,260 of them in existence, ever, in the whole infinite universe of numbers — the largest one has 24 digits. Once you get far enough out, it becomes essentially impossible to keep surviving every single chop.

LEVEL 6

Turning "scary or not" into instant answers

Once we know, for every number up to 999,999, whether it's scary or not, answering a query is still one more small step. A query asks "how many scary primes are ≤ N?" — not "is N itself scary?" So we build one more array: a running count, where entry i stores how many scary primes exist among all numbers from 0 up to i.

count[i]
=
count[i-1]
+
1 if i is scary else 0

Building this running count takes one simple pass through all the numbers, and afterward, every query — even all 100,000 of them — gets answered by looking up a single array entry. No matter how many questions arrive, the hard work only ever happens once.

LEVEL 7

Writing it in Python

Putting Levels 2, 4, 5 and 6 together. First, the sieve (Level 2), then deciding which primes are scary (Levels 4–5), then the running count (Level 6):

scary = bytearray(LIMIT + 1) for n in range(2, LIMIT + 1): if is_composite[n]: continue if '0' in str(n): continue
Level 5's zero-digit trap: reject numbers containing a 0 before even looking at chopping. Non-primes are skipped immediately too.
ten = 10 ok = True while ten <= n: suffix = n % ten if suffix < 2 or not scary[suffix]: ok = False break ten *= 10 scary[n] = ok
Level 4's chopping check: walk through every suffix (last 1 digit, last 2 digits, …) and confirm each one was already marked scary — guaranteed to be known already, since every suffix is a smaller number we visited earlier.
count_upto = [0] * (LIMIT + 1) running = 0 for n in range(LIMIT + 1): if scary[n]: running += 1 count_upto[n] = running
Level 6's running count: one pass, and every query becomes an instant array lookup.

The complete program:

vectar8.py
import sys

LIMIT = 1_000_000

# Step 1: Sieve of Eratosthenes
is_composite = bytearray(LIMIT + 1)
is_composite[0] = is_composite[1] = 1
for i in range(2, int(LIMIT**0.5) + 1):
    if not is_composite[i]:
        for j in range(i * i, LIMIT + 1, i):
            is_composite[j] = 1

# Step 2: figure out which primes are "scary"
scary = bytearray(LIMIT + 1)
for n in range(2, LIMIT + 1):
    if is_composite[n]:
        continue
    if '0' in str(n):
        continue
    ten = 10
    ok = True
    while ten <= n:
        suffix = n % ten
        if suffix < 2 or not scary[suffix]:
            ok = False
            break
        ten *= 10
    scary[n] = ok

# Step 3: prefix counts, so every query is answered in O(1)
count_upto = [0] * (LIMIT + 1)
running = 0
for n in range(LIMIT + 1):
    if scary[n]:
        running += 1
    count_upto[n] = running

# Step 4: answer every query instantly
data = sys.stdin.read().split()
t = int(data[0])
out = []
for i in range(1, t + 1):
    n = int(data[i])
    out.append(str(count_upto[n]))
print("\\n".join(out))
Why read all the input at once?

With up to 100,000 queries, calling Python's input() once per query adds up in overhead. Reading everything in a single sys.stdin.read() call and splitting it into a list up front, then printing all the answers joined together at the end, avoids that overhead entirely — a standard trick whenever a problem promises a large number of queries.

LEVEL 10

Your turn: practice challenges

Work these out with pencil and paper first, then check yourself with the tools above.

Challenge 1: Is 373 a scary prime? Show your chopping work.

373 has no zero digits. Is it prime? Yes. Chop to 73: prime? Yes. Chop to 3: prime? Yes. All checks pass — 373 is scary.

Challenge 2: Is 103 a scary prime? Explain using Level 5's trap.

103 contains a 0 digit, so it's disqualified immediately — not scary — regardless of whether chopping would otherwise work out. (In fact 103 is prime, and 103 % 10 = 3 is prime too, which is exactly the trap: arithmetic alone would miss the zero, which is why Level 5 insists on checking digits directly.)

Challenge 3: Why does the algorithm process numbers strictly in increasing order (2, 3, 4, 5, …) instead of, say, largest to smallest?

Because deciding whether n is scary depends on already knowing whether n's suffix is scary — and the suffix is always a smaller number. If we worked largest to smallest, we'd need an answer for a smaller number before we'd computed it yet — a chicken-and-egg problem. Going smallest to largest guarantees every suffix we ever need to look up has already been decided.

Challenge 4 (harder): Why is it impossible for a scary prime to end in the digit 5 (except for 5 itself)?

Any number ending in 5 that's bigger than 5 is divisible by 5 (since 5 itself divides it), so it can't be prime unless it is 5. Since the single last digit is always one of the "suffixes" that must independently be prime, no scary prime with more than one digit can end in 5 — that final single-digit check would immediately fail. The same reasoning rules out scary primes (other than 2 itself) ending in an even digit.
