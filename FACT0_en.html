The Prime Factory: Factoring 15-Digit Numbers into Recipes

You already know how to break a small number into its prime "ingredients." This problem hands you a whole stack of numbers — some with 15 digits — tells you to keep going until you see a 0, and asks for each recipe written compactly as prime^count. Same idea as before, dialed up to a size where sloppy code finally gets punished.

No math background needed Primes & Loops Interactive
LEVEL 1

The mission, straight from the judge

The input contains several positive whole numbers, one per line — possibly as large as 15 digits — and the input finally ends with a line containing just 0 (which you should not factorize). For every number before that 0, print its prime factorization on its own line, written as p₁^e₁ p₂^e₂ \ldots — each prime that divides it, raised to however many times it divides it, primes listed from smallest to largest.

Straight from the judge

Input: 3111989, 13091989, 77145199750673, then 0 to stop.
Output:
317^1 9817^1
17^2 89^1 509^1
328439^1 234884407^1

Already met prime factorization?

This page builds directly on the Prime Factorization case file, which covers the core idea — testing candidate divisors, dividing them out fully, and the √n shortcut — using numbers up to 10,000. If any of that sounds new, do that page first; here we'll move fast and focus on what's genuinely different at 15-digit scale.

LEVEL 2

Quick refresher: the recipe-finding loop

The core algorithm hasn't changed at all: test candidate divisors d = 2, 3, 4, \ldots; whenever d evenly divides what's left of n, divide it out and keep dividing by that same d until it stops working; move to the next candidate; and stop early once d × d exceeds what's left, since anything remaining at that point must itself be one final prime.

factorize_basic.py
def factorize_basic(n):
    factors = []
    d = 2
    while d * d <= n:
        while n % d == 0:
            factors.append(d)
            n //= d
        d += 1
    if n > 1:
        factors.append(n)
    return factors

This is exactly the algorithm from the Prime Factorization page. It's correct for any n. The rest of this page is about three small but essential changes needed to make it comfortable at FACT0's scale and match its exact input/output shape.

LEVEL 3

New twist #1: nobody tells you how many numbers are coming

Earlier problems usually start with a line like "here comes n, so read exactly n things." FACT0 does something different, common on older judges like SPOJ: it just keeps handing you numbers, one per line, and you're expected to keep reading until you see a sentinel value — here, the number 0 — which signals "that's everything, stop."

read_until_zero.py
import sys

for line in sys.stdin:
    n = int(line)
    if n == 0:
        break
    # ... handle n here ...
Why use a sentinel at all?

It's a simple, old-school trick: instead of the input file needing to announce its own length up front, the data just says "I'm done" when it ends. You'll see this pattern on plenty of classic judges — the rule is always the same: read a value, check if it's the stop signal, and only then decide whether to process it.

LEVEL 4

New twist #2: the output wants p^e, not repeated primes

The Prime Factorization page's output style was 5*7*7 — each prime listed once per copy. FACT0 wants the compact 7^2 form instead: one prime, followed by how many times it divides in. The nice part: we already have that count sitting right there in the inner while loop — we just weren't keeping track of it.

245 = 5 × 7 × 7
→
5^1 7^2

Instead of appending d to a list once per division, count how many times the inner loop successfully divides, and remember the pair (d, count) only if that count is bigger than zero:

count_not_list.py
count = 0
while n % d == 0:
    count += 1
    n //= d
if count > 0:
    factors.append((d, count))
LEVEL 5

New twist #3: at 15 digits, √n stops being optional

In the Prime Factorization page, n only went up to 10,000, so the √n shortcut was a nice bonus — skipping it would only cost you a slow-but-survivable 10,000 steps instead of 100. Here, a number can have 15 digits, close to 1015. That changes everything.

~1015
candidate divisors to check if you test every d up to n itself
~3.2 × 107
candidate divisors to check using the √n shortcut (√1015)

Ten test cases at 1015 steps each is somewhere around ten quadrillion operations — not happening, ever. The same count using √n instead is about 32 million per worst-case number — something a computer can chew through in well under a second. The √n shortcut goes from "nice speedup" to "the entire reason this problem is solvable."

Why the shortcut is still correct at this size

The reasoning doesn't change with size: if what's left of n had two factors both bigger than its square root, their product would already exceed n — impossible. So once d × d passes what's left of n, at most one prime factor can remain, and it has to be n itself. See the Prime Factorization page for the full argument.

LEVEL 6

New twist #4 (bonus speed): skip the even numbers

Here's a small trick worth having once every operation counts: handle the prime 2 by itself first, dividing it out completely. After that, n is guaranteed to be odd — so no even number can possibly divide it again. There's no point ever testing d = 4, 6, 8, \ldots afterward; jump straight from 3 to 5 to 7, skipping every even candidate.

2
then
3, 5, 7, 9, 11, …

This roughly halves the number of candidates you ever have to test after the first step — a simple, free speedup once you know the "leftover" number can never be even again.

LEVEL 7

Writing it in Python

Combining Levels 3–6 with the core loop from Level 2:

count = 0 while n % 2 == 0: count += 1 n //= 2 if count > 0: factors.append((2, count))
Level 6: handle the prime 2 on its own, up front, so every candidate afterward can safely skip evens.
d = 3 while d * d <= n: count = 0 while n % d == 0: count += 1 n //= d if count > 0: factors.append((d, count)) d += 2
Level 5's √n shortcut, Level 4's exponent counting, and Level 6's even-skipping (d += 2 instead of d += 1), all in one loop.
if n > 1: factors.append((n, 1))
Whatever's left over once the loop stops is one final prime, exactly as in the Prime Factorization page.

And the complete program, including Level 3's read-until-zero loop:

fact0.py
import sys

def factorize(n):
    factors = []

    count = 0
    while n % 2 == 0:
        count += 1
        n //= 2
    if count > 0:
        factors.append((2, count))

    d = 3
    while d * d <= n:
        count = 0
        while n % d == 0:
            count += 1
            n //= d
        if count > 0:
            factors.append((d, count))
        d += 2

    if n > 1:
        factors.append((n, 1))

    return factors

for line in sys.stdin:
    line = line.strip()
    if not line:
        continue
    n = int(line)
    if n == 0:
        break
    parts = [f"{p}^{e}" for p, e in factorize(n)]
    print(" ".join(parts))
A note on speed

This Python version is correct for any input — but Python itself is slower per-operation than a compiled language like C++. On the real judge, ~32 million loop iterations for a worst-case 15-digit prime can take a couple of seconds in Python versus a fraction of a second in C++, and SPOJ's time limits were often written with C++ in mind. The algorithm here is exactly what a fast solution uses; if you were submitting for real and hit a time limit, switching languages (keeping the same logic) is the usual fix — not changing the approach.

LEVEL 10

Your turn: practice challenges

Work these out with pencil and paper first, then check yourself with the tool above.

Challenge 1: Factorize 360 by hand into p^e form.

360 = 2×2×2×3×3×5 — three 2's, two 3's, one 5. Answer: 2^3 3^2 5^1.

Challenge 2: What does factorize(n) return for a prime number, like n=97?

The loop never finds a divisor (checking 3, 5, 7… up to √97≈9.8, none divide), so it stops with n=97 still left over and greater than 1. The final check appends (97, 1). Output: 97^1 — exactly what you'd want for a number that's already prime.

Challenge 3: Why is it safe to jump straight from checking 2 to starting at d=3 and stepping by 2 (3, 5, 7, 9, …), instead of also checking 4, 6, 8?

Because the code fully divides out every factor of 2 before that loop even starts. Once that's done, whatever is left of n cannot possibly be even — if it were, it would still have a factor of 2 left, contradicting that we already removed them all. Testing 4, 6, 8, … afterward would always fail, so skipping them wastes zero correctness and saves real time.

Challenge 4 (harder): What would this program print if the input were just a single 1 followed by 0? Is that a sensible answer?

For n=1: the loop for 2 never runs (1 is odd... well, 1 % 2 != 0, so count stays 0), the main loop condition d*d ≤ n is 9 ≤ 1, false immediately, and the final check n > 1 is false too (n is exactly 1). So factors stays empty, and the program prints a blank line. That's actually correct: 1 has no prime factors at all — it's the empty product — so an empty list of factors is the mathematically honest answer, even though it looks a little strange on screen.

Challenge 5: Modify the code so that, alongside each factorization, it also prints how many candidate divisors d were actually tested — useful for seeing the √n shortcut's savings with your own eyes.
fact0_debug.py
def factorize_debug(n):
    factors = []
    tested = 1  # we always "test" 2

    count = 0
    while n % 2 == 0:
        count += 1
        n //= 2
    if count > 0:
        factors.append((2, count))

    d = 3
    while d * d <= n:
        tested += 1
        count = 0
        while n % d == 0:
            count += 1
            n //= d
        if count > 0:
            factors.append((d, count))
        d += 2

    if n > 1:
        factors.append((n, 1))

    return factors, tested
